# Client-Server

**Category:** Architectural · **Also known as:** two-tier, request-response architecture · **Related:** Layered, Broker, Microservices, Proxy, Front Controller

## Intent
Split a system into **servers** that own resources and provide services, and **clients** that request those services over a network. The server is the single authority over shared data and rules; many clients connect to it concurrently.

## Problem
- Several users or devices need to share and modify the same data consistently.
- Business rules and secrets must not live on user devices, where they can be read or tampered with.
- Clients differ (browser, mobile, CLI), but data and rules must be the same.
- Scenario: a team task tracker. Each user keeps a local JSON file; edits collide and nobody sees the same list. Moving data and rules to a server gives one source of truth.

## Solution and structure
```
  Browser (Angular SPA) ─┐
  Mobile app            ─┼── HTTP/HTTPS, WebSocket, gRPC ──► Server (API + rules) ──► Database
  CLI / partner system  ─┘
```
- **Server:** listens on a known address, authenticates, validates, applies rules, persists, responds. Should be stateless per request where possible (session in tokens/DB/Redis) to scale horizontally.
- **Client:** presentation and interaction; may cache and validate for UX, but the server re-validates everything.
- **Protocol/contract:** HTTP+JSON (REST/OpenAPI), GraphQL, gRPC, WebSocket for server push.
- Variants: thin client (server renders), thick client (SPA/mobile with rich logic), peer-to-peer (the opposite style).

## When to use
- Essentially every multi-user web or mobile application.
- Centralized data, authority and security are required.
- Clients of several kinds share one backend.

## When NOT to use
- Offline-first or local-only tools where a server adds latency and failure modes: use local storage, then sync (CRDTs, local-first).
- Peer-to-peer distribution (file sharing, some real-time collaboration) where a central server is a bottleneck.
- Smell: a "chatty" client making 30 requests per screen; add an aggregation endpoint (BFF) rather than abandoning the style.

## Example — Python
```python
# Server: owns state and rules; validates every request; stateless between requests.
from uuid import UUID, uuid4
from fastapi import FastAPI, HTTPException
from fastapi.middleware.cors import CORSMiddleware
from pydantic import BaseModel, Field

app = FastAPI()
app.add_middleware(CORSMiddleware, allow_origins=["http://localhost:4200"],
                   allow_methods=["*"], allow_headers=["*"])

class TaskIn(BaseModel):
    title: str = Field(min_length=1, max_length=200)

class Task(TaskIn):
    id: UUID
    done: bool = False

_tasks: dict[UUID, Task] = {}          # stand-in for a database

@app.get("/tasks")
def list_tasks() -> list[Task]:
    return list(_tasks.values())

@app.post("/tasks", status_code=201)
def create_task(body: TaskIn) -> Task:
    task = Task(id=uuid4(), title=body.title.strip())
    _tasks[task.id] = task
    return task

@app.patch("/tasks/{task_id}/done")
def complete(task_id: UUID) -> Task:
    task = _tasks.get(task_id)
    if task is None:
        raise HTTPException(404, "task not found")
    task.done = True
    return task
```

## Example — TypeScript
```ts
// Client: Angular service + component; validates for UX, but trusts the server's response.
import { Component, Injectable, inject, signal } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { rxResource } from '@angular/core/rxjs-interop';

export interface Task { id: string; title: string; done: boolean }

@Injectable({ providedIn: 'root' })
export class TasksApi {
  private http = inject(HttpClient);
  private base = 'http://localhost:8000';
  list() { return this.http.get<Task[]>(`${this.base}/tasks`); }
  create(title: string) { return this.http.post<Task>(`${this.base}/tasks`, { title }); }
}

@Component({
  selector: 'app-task-list',
  template: `
    @if (tasks.isLoading()) { <p>Loading…</p> }
    @if (tasks.error()) { <p>Server unavailable</p> }
    @for (t of tasks.value() ?? []; track t.id) { <li>{{ t.title }}</li> }
    <input #title /> <button (click)="add(title.value)">Add</button>
  `,
})
export class TaskList {
  private api = inject(TasksApi);
  protected tasks = rxResource({ stream: () => this.api.list() });   // resource APIs are new; check angular.dev
  add(title: string) {
    if (!title.trim()) return;                        // UX check only; server validates again
    this.api.create(title).subscribe(() => this.tasks.reload());
  }
}
```

## In the wild
- HTTP itself, databases (Postgres server + psycopg/asyncpg clients), SMTP, DNS, Redis.
- Every SPA + API setup (Angular + FastAPI/NestJS), mobile apps + backend, gRPC services.
- Browser `fetch`/Angular `HttpClient`, Python `httpx`/`requests` are the client side.

## Trade-offs
| Pros | Cons |
|---|---|
| One source of truth; consistent data and rules | Server is a bottleneck and single point of failure unless scaled |
| Centralized security and updates | Network latency and offline failure on every interaction |
| Clients can be diverse and simple | Contract changes must stay backward compatible for old clients |
| Scales horizontally if the server is stateless | Server cost grows with clients |

## Pitfalls
- **Trusting the client:** client-side validation, price calculation or role checks are UX only. Re-validate and authorize on the server.
- **Sticky in-memory server state:** breaks when you add a second instance. Keep sessions in tokens or a shared store.
- **No timeouts on the client:** hung requests freeze UIs. Set timeouts and show error states.
- **CORS confusion:** CORS protects users' browsers, not your API; configure allowed origins explicitly and still authenticate.
- **Breaking API changes:** version endpoints or evolve additively; mobile clients update slowly.
- **N+1 over HTTP:** list endpoint then one call per item. Provide batched or aggregated endpoints.

## Refactoring path
- **Introduce it:** from a local-only app, move the data model and rules behind an API; keep a client cache; replace file reads with HTTP calls behind a service interface.
- **Remove it / simplify:** for single-user tools, a local database (SQLite, IndexedDB) with optional sync can replace the server.
